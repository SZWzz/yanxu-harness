## 3. 共同架构约束

1. **Core 只有一个。** 调度器管理哪个任务可以运行；实际模型与工具仍由同一 Runner 驱动。reducer 不做 I/O、不读时钟、不访问 worker。
2. **执行证据不迁移所有权。** 工具副作用以 Gateway 或受委托宿主的回执为准；消息入库、任务完成、协程取消都不能证明外部操作成功或未发生。
3. **控制事实有事务边界。** SQLite 参考实现将任务、inbox、Run 状态、控制 outbox 与预算预留放在同一个控制数据库。操作账本与业务数据库仍可独立，跨库依靠稳定身份和核对协议，不宣称分布式原子事务。
4. **终态不复活。** 完成的 Run 和 Task 不因延迟输入、旧 callback 或迟到子结果重新运行。新工作由宿主显式创建新 Task/Run。
5. **输入不授予权限。** 输入类型、目标、身份、子任务能力配置由可信宿主决定；模型与 Skill 不能伪装审批、取消授权或子任务完成事实。
6. **语义与格式分别版本化。** 新任务状态、输入编码、Core 快照、SQLite 布局、诊断、评测摘要均给出版本和兼容路径；旧缺失字段不得补成当前配置。
7. **基础安装保持标准库可用。** 本地 worker 显式启动，无冷导入后台线程、隐式网络、凭据读取或强制外部服务。
8. **文档反映实际交付。** 不把接口草案、待跑平台、脚本模型结果或内存后端写成持久可靠性证明。

## 4. F0–F4：先修复四项验收缺陷

### F0：冻结复现与回归边界

沿用独立验收的 RDE-D1/E1/E2/E3 编号，将四个探针改成测试；提交红测与失败原因，随后分项修复。小样本说明缺陷归入 RDE-E2。

| 编号 | 必须保留的修复前证据 | 修复后的目标 |
| --- | --- | --- |
| RDE-D1 | 7 条事件只返回 `[0,1]`，游标为 6，续读为空 | 连续续读覆盖 0–6，无遗漏与重复 |
| RDE-E1 | 改验收真值或测试命令，摘要仍相同 | 判定条件改变导致身份改变，比较明确拒绝 |
| RDE-E2 | 基线 1 样本、10 tokens 被报成 3 样本、30 tokens | 原始样本只计一次，缺失匹配可见 |
| RDE-E3 | 保留 262145 字符后才裁剪为 2000 | 采集阶段已有明确字节上限，不随总输出增长 |

保持原 PTR-R1/R2/R3 的漂移拒绝、恢复期限和失败回执收敛回归通过。

### F1：分页以实际返回事实推进

- 分清读取起点、已扫描高水位、实际返回事件位置；`next_cursor` 不得跨过已扫描但未返回的匹配事件。
- 达到收集上限后停止积累；若已读入一页，剩余匹配事件必须留给下次续读。全局 cursor 仍可越过确定不属于本 Run 的事件。
- `truncated`、`scan_limit_hit` 和结束判断分别说明，不把“恰好满页”猜成“后面一定为空”。参数验证拒绝无效界限。
- 同一事实边界重读确定；活跃写入按既有 non_atomic/incomplete 规则说明，不为了拼齐报告无限追赶。

验收：小上限、默认 2000 上限、多 Run 交错、空匹配页、尾部无匹配、页边界与收集边界重合，以及按 next_cursor 读到结束后的序号集合与独立存储读取相同。

### F2：冻结完整评测身份与摘要兼容

- `EvalCase` 的规范化身份包含 `expectations` 等所有影响任务或验收的值；`FixtureSpec` 包含测试 argv，不能只包含文件内容。
- F4 引入的命令超时、输出处理策略等实际执行配置，也纳入对应身份。核对声明值与执行值，避免“摘要记录了预算但执行器没用”。
- 字典键顺序不影响摘要，argv 顺序、真值、夹具、验收器和执行约束的变化必须影响身份。嵌套数据防止外部修改悄悄改变已冻结任务。
- 为摘要算法引入显式版本。可以同时升级案例版本或报告 schema，但必须解释旧样例：旧摘要可读、可信比较能力不足时列为 legacy/incomparable，不能用新算法回填旧结果后宣称可比。
- 结果携带实际采用的案例与配置身份；拒绝缺失关键身份、未知摘要算法或不一致的输入。不要让读入 JSON 中的任意 `digest` 字符串替代必要校验。

验收：只改真值、只改测试命令、只改命令策略、只改嵌套配置都不可比；规范化顺序变化仍可比；旧/新与未知版本有明确结果。重新生成样例时保留旧记录的适用范围与历史缺陷。

### F3：一对一匹配与真实样本统计

- 删除缺少 repeat 索引时回退 `candidates[0]` 的补齐逻辑。逐次比较使用案例身份 + repeat_index 等冻结样本键，一对一匹配；重复键拒绝或明确标为 invalid。
- 缺失项进入 unmatched/incomparable，报告实际分母；不得复制基线填满候选。比较范围内的统计和整份原始运行统计分别标明。
- 分布比较独立汇总两边原始有效样本，允许数量不同但必须展示数量、缺失与覆盖，不建立伪配对。
- 每个案例、每一侧分别统计有效真实模型样本；五个案例各一个观测不能算每案例五次。缺失/未运行不充当有效样本，小样本不宣称显著提升。
- 成本与耗时从唯一原始观测汇总，保留 actual/estimated/unknown 与单位；重复引用不能增加费用、耗时样本或质量权重。

验收：1 对 3、索引不连续、重复键、不同案例、全未运行、基础设施错误、多案例少样本；前述 10 tokens 的基线仍只计 10，不变成 30。

### F4：命令执行时即限制输出

- 为前提检查、工具测试命令和最终验收器复用一个有界命令执行器，保留 argv、cwd、显式编码与超时。
- stdout/stderr 同时持续读取，分别或共享有明确字节限额。第一版采用**保留有界输出、继续排空到结束/超时**；达到限额标记 truncated，记录保留字节和可观测丢弃量。读取缓冲本身也要有界。
- 若支持“输出超限立即停止”，作为显式策略：停止、等待并回收本次拥有的进程/任务，报告 output_limit_exceeded，不能伪装测试断言失败或返回 exit 0。
- 命令执行期限与上层剩余期限取最小值；停止后的清理单独设置有界宽限，不恢复业务派发，也不无限等待管道或遗留后台读取任务。不得将无界输出转存临时文件规避上限。已有结构化调用者需要适配新执行结果，不依赖未定义字段。
- POSIX / Windows 的子进程及后代清理能力分别实现并声明；未能证明已停止的外部工作标记未知。仅执行过的系统才写成验证通过。
- 摘要输出仍做路径/秘密形状清理和 Markdown 转义；限制采集量不能取消公开报告的白名单规则。结果记录实际输出策略，并与 F2 摘要接通。

验收：stdout/stderr 同时大量输出、超长单行、分块多字节字符、持续输出超时、取消、错误退出、管道未关闭；用计数器证明保留量不随总量增长，不依赖一次高风险 OOM 压测证明缺陷。

**F 门禁：** 四项红测转绿、原恢复回归通过、比较和样例兼容说明更新，再进入持久编排的运行接线。

## 5. Q0：冻结身份、输入与任务状态契约

### 5.1 对象与所有者

| 对象 | 本轮定义 |
| --- | --- |
| namespace | 租户/项目隔离边界，由宿主建立 |
| session | 会话分组；不是共享所有任务状态或权限的容器 |
| task | 一个可排队、等待、取消、验收的工作单元，关联一个固定逻辑 Run |
| run | 现有 Core 执行的权威事实，不因 worker 变化而换 ID |
| attempt | 一次取得执行权的尝试；重领后新 ID，逻辑任务和预算不重置 |
| input | 一条已接纳的有序输入，具有稳定 input_id、内容摘要、目标与消费事实 |
| child relation | 父任务、稳定 spawn 身份、子任务、授权配置与预算预留的控制关系 |

第一版一个 Task 绑定一个 Run。完成后的新用户请求显式创建新 Task/Run，并可关联原 session；不隐式重开已终结 Run。审批和崩溃恢复继续属于原 Run。

### 5.2 输入类型与接纳结果

- 用户输入明确区分 initial、steering、follow_up；取消、审批决定、child_completed 是可信控制入口或内部通知，不能由普通模型文本指定类型后取得控制权。
- 幂等键至少覆盖 namespace/task/input_id，内容摘要包括类型、目标、内容及语义参数；相同键相同内容返回原接纳结果，不再次扣积压额度；相同键不同内容冲突拒绝。
- 返回 accepted / duplicate / refused、稳定序号、目标身份和拒绝码。accepted 仅表示可靠保存，不等于模型已经读取或任务成功。
- 冻结每类输入的轮询位置、`all` / `one-at-a-time` 顺序、优先级与积压界限，复用现有 steering/follow-up 的语义。steering 不强行打断已经派发的工具或模型请求。
- Task/Run 终态后提交明确拒绝；取消先获胜时输入不得继续派发；接纳先获胜后又取消，输入保留为未应用/已取消事实，不从存储消失。

建议 Task 状态覆盖 queued、running、waiting、cancelling 及带原因的 completed/failed/cancelled/usage_limited；Q0 提交状态表和所有边。TaskStatus 与 RunStatus 分别有用途：排队不伪造运行，调度等待不伪造模型成功。

### 5.3 能力端口

新增一个可选的协调存储端口，组合任务、inbox、控制 outbox 和预算预留；名称可按仓库风格确定。要求的原子操作至少包括：

1. 接纳初始任务及 initial 输入，固定 Run ID，重复提交返回同一结果。
2. 按目标状态接纳输入、分配序号、更新 inbox revision。
3. 领取/续租/释放调度工作，带持久 fencing token。
4. 在同一事务提交 Run 迁移、输入消费确认、相关事件及需要的控制通知。
5. 按租约与额度准入派发、幂等结算预算；原子登记 child、预算预留及调度 outbox。

这是新能力建议，不是当前 `Persistence` 已有的方法。只启用单 Run 的旧后端无需实现全部扩展；显式启用持久任务却缺少原子能力时，在执行前拒绝，不能退回两次独立写入。

## 6. Q1：持久 inbox 与控制存储

### 6.1 存储事实

建议模型包含 TaskRecord、InputRecord、DispatchClaim、ChildRelation、ControlOutbox、BudgetReservation；尽量使用简单版本化数据。序号、状态变化、重试次数、来源、fencing 和内容摘要都需要可查询，不把 callable、协程或私有凭据序列化。

输入状态至少区分 pending、claimed、applied、cancelled/refused。claimed 只是临时消费权；applied 必须引用产生接纳效果的 Run revision / 事件，不用“从队列取出”作为应用证明。

applied 表示输入已纳入持久执行状态，不承诺模型已经看到或必然采用该文本。之后可能因上下文预算、取消或权限检查停止，诊断需要如实展示这些后续结果。

- 同一个 SQLite 控制库中的接纳、领取、应用、outbox 和迁移使用真实事务及唯一约束。同步增加内存参考实现，但明确 VOLATILE。
- 租约有效性、任务状态、inbox revision、容量与唯一键在事务内重读；不依赖先查再写的进程内锁。
- 领取具有截止、最大批量、重领与公平排序。过期 claim 不代表工具没执行，恢复仍先看 Run 和操作证据。
- 积压按任务、namespace 和总量有界，包含条数与载荷字节；达到容量明确拒绝或背压，不能挤掉已经 accepted 的输入。
- 去重记录与消费标记有保留期限；不因删除消息正文而重新接受旧 ID。首版不自动清理必要证据，记录容量与后续清理约束。
- 读取和运维查询核对身份并分页；诊断连接不迁移表、不领租约、不确认输入。

验收：两个真实连接/进程同时提交同一输入、不同内容冲突、容量竞争、领取后死亡、租约转移、旧 worker 确认失败、读写隔离。重启后保持序号和去重结果。

### 6.2 存储升级

为控制库新增布局做版本升级，写入入口明确迁移，诊断只读入口明确兼容范围。升级在事务内完成；未知未来版本拒绝。旧 Run/审批/账本保持可读，旧原始 API 不会自动创建 Task 或假装拥有输入消费记录。

## 7. Q2：在同一 Core 中可靠消费输入

### 7.1 持久输入接线

Runner 在原 `ReadInputs` 边界读取带稳定引用的输入批次；归约器接收消息和输入身份，产生新状态。输入引用、已应用水位和待确认集合必须进入版本化快照。

不能直接把 inbox 包装成一个返回普通消息的破坏性 `drain()`：进程可能在读取后、状态提交前退出。旧内存回调仍保留；持久输入与旧回调同时配置时，明确组合规则，首版推荐拒绝同一通道的双重来源。

### 7.2 原子应用边界

```text
读取候选输入（不确认）
  → reducer 接受带 input_id 的事件
  → 控制存储原子提交：Run 快照 / transcript 增量 + input applied + 事件
  → 才允许准备并派发后续外部工作
```

- 初始输入也遵循这一边界：创建 Run、保存初始可恢复快照与确认 initial 输入不能产生永久缺口。
- 现 `_state_sink` 跳过 COLLECTING；本轮需识别“有持久输入应用”的迁移并提交，不能照搬旧优化。
- 崩溃发生在提交前，输入仍可重领；发生在提交后、外部派发前，从已提交状态继续，不再追加同一输入。
- 初始/输入接纳后但尚无 batch 的恢复，需要明确支持的快照相位与 Runner 恢复入口，仍复用 `_drive`。只恢复能够证明没有未结算外部动作的边界；不把历史无快照孤儿记录猜成安全初态。
- 已派发模型请求是否可以重发遵循明确策略，不能以 inbox 恢复为理由默认“模型没执行/没计费”。工具批次继续采用原证据恢复。

### 7.3 结束竞争与暂停输入

- **空读与终态提交之间的竞争必须处理。** 终态事务检查已观察的 inbox revision 和可消费输入：新输入先接纳，则重新走既有轮询边界；终态先提交，则新输入拒绝。不能 accepted 后静默丢掉，也不能终态被旧回调复活。
- 明确 steering/follow-up 在审批、工具核对和子任务等待期间的处理：可以暂存，不能暗中批准操作、改写已批准参数或越过 unknown 屏障。真正纳入上下文时重新准备请求与预算。
- 输入消费失败或存储冲突停止新派发，晚到结果仍按 attempt/fence 和操作证据处理。

验收使用进程握手/提交钩子控制四个窗口：接纳后未领取、领取后未提交、应用后未派发、空读后终态前。另测同 ID 重投、旧 attempt、积压、取消、预算和暂停状态；断言会话只出现一次对应输入，工具不会因重投再执行。

## 8. Q3：有界多任务调度

### 8.1 本地参考 worker

- 提供宿主显式调用的 submit / run_once / run_until_idle / stop / query 等库入口，名称以实际实现为准。默认按需运行，不启动隐式守护进程。
- 调度器只挑选、领取和恢复 Task，调用现有 Harness；不自己发送模型请求、不手工重新实现工具批次。
- 单任务一个逻辑执行者；同时存在调度 claim 与 Run lease 时固定获取/释放顺序。最终执行与提交以 Run fencing 为准，调度 claim 不能绕过它。
- 取得 claim 后重读任务、取消标记、Run 和配置。Run 已存在时分类为终态、等待、仍有合法执行者或可恢复孤儿；不能重新 start 一个新 Run 冒充重试。
- 首版简单有界队列：全局/namespace 并发上限，namespace 轮转加同级 FIFO，有限优先级与老化避免饥饿。具体排序规则在 Q0/Q3 文档冻结。
- waiting 任务释放执行槽；外部决定或子结果持久化后再次变为可调度。等待期间不忙轮询、不占满可运行并发。
- claim/Run lease 的续期和最长期限显式有界。丢失执行权停止新派发；不要把租约过期当成远端工具已停止的证明。

### 8.2 取消、停机与工作区

- 任务取消是持久请求，与输入接纳和领取有确定竞争顺序；queued 取消不启动 Run，running 取消传到既有驱动，waiting 取消不依赖内存里的 live task。
- 区分停止 worker 与取消业务任务。优雅停止停止领取、限时等待/释放本地资源；进程被强制结束后由原身份与证据恢复，不改成无依据的 completed。
- 宿主提供工作区引用与访问策略；默认对子任务隔离工作区。允许共享写工作区时明确串行/版本控制，不能只有限制 worker 数就宣称无数据冲突。
- 不确定外部写入涉及的资源，未经核对不得释放成“可安全重做”；独立任务的失败不能取消无关任务。

验收：两个 worker 竞争同任务、lease 转移、单任务等待而其他任务继续、持续高优先级输入下普通任务仍可推进、停止后新 worker 接管、独立任务隔离。

## 9. Q4：跨恢复与父子共享预算

- 固定 root_task_id；按逻辑任务树保存额度、预留、实际结算与未知开销，去重键使用稳定派发/预留身份。
- 模型开销按真实 request instance 区分：恢复后重新发送可能再次计费，不能用相同 logical model action 抹掉第二次支出；工具回执 replay 则不伪造第二次 handler 开销。
- 任务级绝对 deadline 持久化，重启后计算剩余期限并在进程内转为单调计时；不跨进程相减 monotonic 值。保留现有 `max_runtime_seconds` 的 invocation 语义，并与任务剩余期限取最小值。
- 先提供可硬约束的轮次/派发次数、并发、任务数、深度和时间预算。实际 token/费用延迟或缺失时如实记录；估算不宣称为实报，不凭未知计费退还全部额度。
- 请求输出上限、上下文/摘要预算与任务额度接通。预算检查和预留必须先于外部 await；提交失败不派发；重放已有回执不再次预留。
- 父任务给子任务预留有界 grant，分配不会增加 root 总额度。完成、失败、取消、启动失败和未知效果分别结算；晚到 usage 幂等补记，不能重复退款或使可用额度变大。
- 取消请求不能立刻释放尚未确认停止的外部开销预留。模型请求已进入派发窗口但没有最终 usage 时保持未知覆盖。

验收：父子竞争最后额度、重复 spawn/完成通知、恢复后额度不刷新、摘要取消仍计费、启动前失败回收预留、派发后未知保留预留，以及已过 deadline 时模型和工具都不再派发。

## 10. Q5：可恢复 subagent 与结构化等待

### 10.1 第一版边界

实现本地父子任务树：默认 root 深度为 0，子任务深度为 1；更深嵌套和任意任务互等不在首版承诺。宿主提供 Agent profile、允许工具、工作区、结果结构和预算上限，模型只能从获准配置中提出子任务。

有效权限由宿主约束、父任务获准委托范围和 child profile 求交集；不从父提示词或子结果中提取权限。子任务有独立上下文、Run/attempt 和受限工作区；namespace 仍保持正确租户归属。

### 10.2 启动与幂等

- 通过经过 Gateway 授权的控制工具提出 spawn；模型生成的 spawn 请求仍受工具可见性、参数验证、权限和预算检查。
- 稳定 spawn 身份绑定父 task、模型动作和工具调用；同一次恢复重投返回原 child，相同身份不同配置拒绝。不同动作中的相同文字不自动合并成一个 child。
- 在控制库原子检查父状态、取消标记、执行权和额度，创建 ChildRelation、child Task、预算预留与调度 outbox，再允许 child 执行。父取消先提交则拒绝 spawn，spawn 先提交则 child 纳入取消传播。Gateway 记录该操作回执，关系表只引用 operation_id。
- 控制库提交与 Gateway 回执可能不在同库：登记后、回执前崩溃时，按稳定 spawn 身份查询 ChildRelation 作为业务证据收敛，不能再创建一个 child 或新建第二份工具账本。

### 10.3 等待、结果与父任务恢复

- 显式等待表现为带 child 引用的持久 pending interaction；父 Run 暂停并释放 worker 槽，等待中不持有数据库事务。
- 父提交正常终态前检查所属 child：仍有活动 child 时先进入持久 join/等待，或执行宿主明确选择的取消并结算策略，不能先把父标为完成再留下活动 child。该终结屏障在 Run 终态前执行，不能靠复活终态实现；子失败如何影响父结局由显式策略决定。
- 如果通过控制工具表达 wait，补齐类型明确的 `child_result` 等待/恢复分支，沿用原工具批次和同一 Runner。当前 resume 对无 batch 的暂停会拒绝，不能直接给 pending_interaction 加字段就声称支持；若采用非 batch 控制动作，必须同时交付对应快照相位、事件和恢复入口。
- 完成事实来自 child 的已提交结局；模型自称完成不能构造内部完成通知。child 终态与待通知 outbox 在同一控制事务中提交，通知允许重投，父输入按稳定 ID 去重。
- 通知只是唤醒线索；父恢复时重新读取 child 记录、验收结果与权限配置。消息丢失时可从 outbox 重试，不靠当前进程内 future。
- ChildResult 至少包含身份、结局/原因、结构化结果或受控产物引用、验收状态与用量覆盖。结果内容作为不可信任务数据进入父上下文，不进入 system 权威指令。
- 首版 wait 仅允许父任务等待自己的 child；拒绝外部/跨租户 child、重复配置冲突、环和超深关系。并发上限为 1 时也必须完成“父暂停 → 子运行 → 父续跑”。

### 10.4 取消、失败与验收

- 默认取消整棵所属子树，先持久记录传播意图；首版不允许模型创建 detached child。父已终态时迟到子结果归档但不复活父任务。
- 父取消与 child 完成按事务事实与稳定身份幂等结算；保留已经发生的副作用和未知项，不能直接删除 child 或伪造未执行。
- 子失败、超限和取消作为不同结果交给父策略；不默认无限重试。重试需要新的显式 attempt/任务决策、剩余额度和幂等约束。
- 提供宿主可配置的独立结果验收器；Schema 通过只证明格式，业务验收失败必须可见。工作区合并或业务写入仍走宿主授权路径。

验收：child 创建后回执前死亡、child 完成后通知前死亡、父收到结果后提交前死亡、重复完成通知、并发 1、预算耗尽、父取消、子失败、跨租户和伪造通知。

## 11. Q6：诊断与任务评测随实现补齐

### 11.1 可解释事实

串起 task/run/attempt、input_id/序号/应用 revision、claim/fence、父子关系、spawn operation、预算预留和控制 outbox。展示排队原因、等待对象、取消传播、实际 worker 与缺失证据。

新增事件在原事务写入，沿用 envelope 和公开白名单。历史 origin attempt 与当前观察者分开；不公开原始任务文本、凭据、绝对工作区路径或子结果全文。只读查询不消费 inbox、不确认 outbox、不续租、不推进父子任务。父子列表和输入历史分页有明确上限。

### 11.2 冻结离线场景

在 F2 的新摘要规则下增加以下案例，使用真实 Harness/SQLite/Gateway 和独立验收器：

| 案例 | 必须由验收器检查的事实 |
| --- | --- |
| inbox 重投与跨进程消费 | 相同输入只进入会话一次，重投不增加工具副作用 |
| 接纳/终结竞争 | accepted 输入最终可查询应用或取消结果；终态后输入明确拒绝 |

| 父取消与迟到结果 | 子树停止新派发，证据保留，父终态不复活 |
| 父子共享预算 | 所有 attempt 和子任务共用有限额度，未知开销不当零 |
| 输出/分页/摘要/样本修复 | 原四项复现转为明确成功断言，基线失败仍保留 |

默认离线且不调用真实模型。可重复性使用冻结任务、工具/权限/预算配置和案例摘要；实际进程终止与模拟故障分别标记。真实模型另行显式配置，不作为本轮离线验收的隐含条件。
